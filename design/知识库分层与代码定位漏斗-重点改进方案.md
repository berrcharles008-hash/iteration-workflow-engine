## 零、定位：为什么聚焦这两个维度

在[腾讯SKILL工作流借鉴分析](./腾讯SKILL工作流借鉴分析.md)（2026-07-24）中，我们识别了 8 个可借鉴项（B1~B8）。当前 `iteration-workflow` 在**门禁体系**和**阶段管理**上已经成熟（7 阶段引擎 + 三道门禁 + P-042 强制委托），但在以下两个维度存在**明确的、可独立改进的空间**：

| 维度 | 当前短板 | 文章启示 |
|------|---------|---------|
| **知识库分层** | specs 活文档是"平铺的完整清单"，定位时要么全量加载（token 大），要么无索引漫游 | L1/L2/L3 三级金字塔，token 压缩 300× |
| **代码定位漏斗** | 靠 code-explorer 子代理一次性大规模搜索，没有分级收敛 | 五步定位法，每步严格限制输入量，漏斗式缩小范围 |

这两个维度是**正交的**——知识库建好能直接加速定位漏斗的第 1、2 步。它们是 `mailplugin-feature-dev` 达成 94% 代码生成率的底层工程基础。

## 一、知识库分层：从"平铺清单"到"三级金字塔"

### 1.1 当前现状

```
.codebuddy/specs/
├── backend-api-endpoints.md      # 41 个 API 端点清单
├── backend-entities.md           # 237 个 Entity/IMgr/BLL 核心文件
├── frontend-pages.md             # 24 个业务模块页面/组件清单
└── frontend-net-bll-map.md       # Net→BLL→Domain 调用链 + csproj 注册表

**问题**：
- 4 个文件是**按技术层划分**的完整清单（后端 API / 后端 Entity / 前端页面 / 调用链），不是按"AI 定位需求"的认知层级组织的
- 定位代码时需要全量加载某个文件（如 `backend-entities.md` 237 个文件），token 消耗大
- 缺少"总览 → 按需展开"的分层入口

## 二、代码定位漏斗：从"全量搜索"到"五步收敛"

### 2.1 当前现状

- 03 阶段 step-1-explore 使用 `code-explorer` 子代理一次性搜索
- 搜索结果可能包含大量文件，token 消耗不可控
- 没有"先看目录结构缩小范围，再逐步深入"的漏斗机制

### 2.2 目标：五步定位法映射

将文章的五步定位法直接适配到我们的技术栈和工作流中：

| 步骤 | 输入量 | 操作 | 产出 | 对标我们哪个阶段 |
|------|--------|------|------|-----------------|
| 1. 意图消歧 | L1 总览 ~2K token | 读 `L1-overview.md`，把产品需求映射到 2-3 个候选模块 | 候选模块清单 | 01→03 过渡 |
| 2. 模块定位 | 1-3 个 L2 模块文件 | 读候选模块的 L2 wiki，锁定具体文件（不读源码） | 2-3 个候选文件路径 | 03 step-1 |
| 3. 关键词搜索 | **不进 LLM**，`search_content` 直接跑 | 用 L3 语义桥扩展搜索词（五维矩阵），grep 命中 | 函数声明 + 位置 | 03 step-1 |
| 4. 调用链追踪 | 单文件相关片段 ~10K | `read_file` 只读命中的相关函数，追踪调用链 | 完整调用链 | 03 step-1 |
| 5. 验证确认 | 函数实现 ~5K | 读最终改动点的完整实现，确认匹配需求 | 最终改动点 + 理由 | 03 step-2 |

**Token 消耗对比**：

| 方式 | Token 估计 |
|------|-----------|
| 当前：全量加载 4 个 spec → code-explorer 一次大搜索 | ~50K-200K |
| 改进后：L1(~2K) → L2(1-3个,~15K) → grep(不进LLM) → 片段(~10K) → 实现(~5K) | ~25K-32K |

### 2.3 五步定位法嵌入 03 阶段的流程改造

```
03-技术方案/step-1-explore（改造前）：
  code-explorer 子代理 → 搜索整个前后端目录 → 返回所有匹配文件

03-技术方案/step-1-explore（改造后）：
  Step 1.1 读 L1-overview.md（~2K token）→ 候选模块 2-3 个
  Step 1.2 读候选模块的 L2 wiki（~15K token）→ 候选文件 2-3 个
  Step 1.3 search_content 精确 grep（不进 LLM）→ 命中行
  Step 1.4 read_file 读命中函数上下文（~10K token）→ 调用链
  Step 1.5 验证确认（~5K token）→ 最终改动点
```

### 2.4 五维搜索矩阵的原生化

把这个概念内置到 `search_content` 的使用模式中——不是一次搜索一个词，而是按 5 个维度交叉展开：

```
产品描述：「分诊评估页新增 绿色通道 快速入口」

↓ 五维展开 ↓

① 平台API（前端）:
   search_content "created|mounted|activated" --glob "*.vue"  → 生命周期入口
   search_content "@WebApi|WebApiMethod" --glob "*.cs"        → 后端路由入口

② 功能语义（由 L3 语义桥驱动）:
   绿色通道 → search_content "GreenChannel|greenChannel|GREEN_CHANNEL"
   快速入口 → search_content "QuickEntry|quickEntry|FastEntry"
   分诊评估 → search_content "TriageAssessment|triageAssessment|TRIAGE_ASSESSMENT"

③ 命名习惯（项目约定）:
   前端: search_content "handle.*Green|on.*Channel|open.*Quick" --glob "*.vue,*.ts"
   后端: search_content "GetGreen|SaveGreen|QueryGreen" --glob "*.cs"

④ Entity/DTO 关联:
   search_content "GREEN_CHANNEL" --glob "*.cs"  → Entity 表名
   search_content "GreenChannel" --glob "*.cs"   → DTO/Mgr/BLL 类名

⑤ 跨层通信:
   前端: search_content "axios.*green|emit.*channel|dispatch.*green"
   后端: search_content "IoC.Resolve.*Green|Autofac.*Green"
```

### 2.5 与 L1/L2 知识库的联动

定位漏斗的第 1、2 步直接消费知识库：

```
Step 1（意图消歧）
  └→ 读 L1-overview.md → 返回「triage-assessment」（候选1）」+「green-channel」（候选2）
  
Step 2（模块定位） 
  └→ 读 L2-modules/triage-assessment.md + L2-modules/green-channel.md
     → 锁定文件：
       - 前端: triage_assessment.vue, triage_assessment_domain.ts
       - 后端: TriageAssessmentBLL.cs, GreenChannelBLL.cs
     
Step 3（关键词搜索）
  └→ 只在已锁定的目录内 grep，先用 L3 语义桥扩展搜索词
     → 高命中率、低噪声
```

这正是文章说的 **1+1 > 2** 效应。

### 4.1 外部路径依赖风险（2026-07-28 补充）

> `mailplugin-feature-dev` 的知识库在 skill 内部的 `references/project_wiki/` 下（见原文十三·④），
> 而本项目的 specs 在 skill 目录外（`.codebuddy/specs/`）。这导致跨项目迁移和跨工具寄宿时存在路径断裂风险。

#### 问题分析

```
mailplugin 做法（skill 自包含）：
  skills/mailplugin-feature-dev/
  └── references/
      └── project_wiki/              ← 知识库在 skill 内部的 references 子目录
          ├── overview.md            ← L1
          └── *.md                   ← L2

本项目当前做法（外部依赖）：
  .codebuddy/
  ├── specs/                         ← 知识库在 skill 外
  │   └── *.md
  └── skills/
      └── iteration-workflow/
          └── engine/phase-03.md     ← 引用外部路径

问题：
  1. skill 引擎引用外部路径，换项目后路径不存在 → 永远无法自动建 L1
  2. 引擎同步到 D:\sj-skills\iteration-workflow-engine 时，specs 跟不过去
  3. 寄宿在不同工具时，工作目录不同，相对路径可能解析失败
```

#### 推荐：对齐 mailplugin 模式，知识库放入 skill 的 `references/` 子目录

```
.codebuddy/skills/iteration-workflow/
├── SKILL.md
├── engine/                          ← 流程引擎（阶段定义/门禁/模板）
├── references/                      ← 静态参考数据（对标 mailplugin 的 references/）
│   └── specs/                       ← 项目知识库（本次新增）
│       ├── backend-api-endpoints.md
│       ├── backend-entities.md
│       ├── frontend-pages.md
│       ├── frontend-net-bll-map.md
│       └── L1-overview.md           ← 自动生成也在此
└── ...
```

> **命名选择**：用 `references/specs/` 而非 `references/project_wiki/`，因为 `specs` 是本项目已建立的术语（MEMORY.md/specs/活文档），改名会增加迁移认知负担。

**收益**：

| 维度 | 效果 |
|------|------|
| 跨项目迁移 | skill 搬到哪，specs 跟到哪，路径永不失效 |
| 引擎同步 | `references/` 是项目数据，sync 时自然排除，不污染引擎 |
| 路径统一 | skill 内引用为 `references/specs/xxx.md`，不依赖外部 |
| 分离清晰 | `engine/`（流程逻辑）与 `references/`（参考数据）分工明确 |
| 对齐 mailplugin | 同样的 `references/` 组织模式，降低学习成本 |

> **注**：本项目当前 specs 在 `.codebuddy/specs/`，迁移到 skill 内需同步更新 MEMORY.md 中的路径引用和 `specs/` 活文档相关描述。

#### 4.1.1 迁移步骤（具体操作）

| 步骤 | 操作 | 风险 |
|------|------|------|
| 1. 创建目标目录 | `mkdir -p references/specs/L2-modules/` | 无 |
| 2. 复制 4 个 spec 文件 | `cp .codebuddy/specs/*.md references/specs/` | 低（纯读操作） |
| 3. 生成 L1-overview.md | 执行 `gen-l1` 命令（见 6.6） | 低（自动生成） |
| 4. 验证路径 | Agent 重启后，检查 L1 加载是否命中 `references/specs/` | 中（需确认引擎优先读取新路径） |
| 5. 标记旧路径废弃 | 在 `.codebuddy/specs/` 下放置 `README.md`：`> 知识库已迁移至 references/specs/，本目录保留为历史参考，不再维护` | 低 |
| 6. 删除旧文件（可选） | 确认一切正常后删除 `.codebuddy/specs/` 下 4 个 spec 文件 | 中（建议保留至少一个迭代周期） |

> **过渡策略**：步骤 2-5 不影响现有功能（新旧并存），步骤 6 可选延迟。详细并行策略见 6.8。

### 4.2 specs_dir 配置变量：引擎如何知道知识库在哪

> 4.1 解决了"知识库放哪"，但引擎需要知道这个位置。如果路径硬编码在 `phase-03.md` 中，换项目/换工具后路径可能失效（P-041 同类问题）。

#### 推荐做法：SKILL.md 顶部声明配置变量

```yaml
# SKILL.md 顶部 YAML frontmatter
config:
  specs_dir: references/specs/          # 知识库根目录（相对于 skill 目录）
  specs_fallback_dirs:                   # 回退搜索路径（按优先级）
    - .codebuddy/specs/                  # 旧项目可能还在用旧路径
  l1_file: L1-overview.md               # L1 文件名
  l2_dir: L2-modules/                    # L2 子目录
  l3_file: L3-glossary.md               # L3 文件名
```

**Agent 加载逻辑**（写入 `engine/phase-03.md` 的 step-1 前置步骤）：

```
1. 读 SKILL.md 顶部 config.specs_dir
2. 解析为 ${SKILL_ROOT}/${specs_dir}/
3. 检查该路径是否存在 → 是：使用；否：尝试 fallback_dirs
4. 所有路径都不存在 → 走 6.6.1 数据源层级（目录扫描自动推断）
```

**收益**：
- 路径变一次只改一处（SKILL.md 顶部），不用逐个 engine 文件修改
- 新项目接入时修改 `specs_dir` 即可，不碰引擎逻辑
- 回退路径数组化，支持多 IDE/多工具寄宿

## 五、核心结论

`mailplugin-feature-dev` 最值得借鉴的不是它有几个阶段（我们已有更细的 7 阶段），而是它**把"AI 定位代码"这件事从"凭运气 grep"变成了"有地图的导航"**。

实现路径清晰且低风险：
1. **知识库分层**：把平铺的 spec 拆成 L1 总览 + L2 模块 + L3 语义桥（结构改造，不改逻辑）
2. **代码定位漏斗**：把 03 的 code-explorer 自由搜索改为 5 步收敛（流程改造，不改门禁）

这两个改进**正交于现有门禁和阶段管理体系**，可独立推进，互不阻塞。

## 六、渐进式兼容：策略模式设计（2026-07-28 补充）

> 原始方案假设 L1/L2/L3 全部建好后再启用漏斗。但实际落地需要渐进式推进——写完一个模块的 L2 就立即生效一个模块，不等全部完成。

### 6.1 核心设计：五步漏斗的数据源采用策略模式

五步漏斗的 Step 1-2 数据源可插拔，Step 3-5 完全不变：

| 子步骤 | 功能 | 优先数据源 | 回退数据源 | 切换条件 |
|--------|------|-----------|-----------|---------|
| 1.1 | 意图消歧 | `references/specs/L1-overview.md`（~2K token） | 按 6.6.1 数据源层级逐级尝试（specs 4 文件 → README/docs → 目录扫描） | L1 文件存在性 |
| 1.2 | 模块定位 | `references/specs/L2-modules/{module}.md` | 执行 `list_dir` 扫描候选模块前后端目录 | L2 文件存在性 |
| 1.3 | 精确搜索 | `search_content` 目标目录 | 不变 | — |
| 1.4 | 片段读取 | `read_file` 命中函数 | 不变 | — |
| 1.5 | 验证确认 | `read_file` 改动点 | 不变 | — |

### 6.2 效果

- **今天**（L1/L2 不存在）：自动走回退路径，用现有 specs + list_dir，功能完全可用
- **渐进中**（部分 L2 已建）：命中模块走 L2 加速路径，未命中模块走回退路径，模块级别渐进
- **完成后**（全量 L1/L2）：自动全走知识库路径

### 6.3 对已有路线图的调整

原有 S1→S2→S3→S4 顺序依赖被打破：

| 原路线图 | 调整后 |
|---------|--------|
| S1 建 L1+3个L2 → S2 改 03 流程 | **S2 可先行**（无 L1/L2 也能跑漏斗，见 2.2 Token 对比中的回退消耗） |
| S2 依赖 S1 完成 | **S1 和 S2 解耦**，S2 用策略模式保证兼容 |
| S3 补全剩余 L2 | S3 不变，每补一个 L2 该模块自动受益 |

**推荐顺序**：**S1 和 S2 并行推进**。S2 改造漏斗流程本身（Step 1-2 先走回退路径），S1 同步建 L1+核心 L2。原因：
- S2 单独改造也有收益——Step 3-5 的精确搜索 + 片段读取 + 验证确认，即使 Step 1-2 走回退也比当前的 code-explorer 全量搜索更可控（见 2.2 Token 对比）
- 但 S2 的最大加速效果（300× token 压缩）必须等 S1 的 L1/L2 就位后才能体现（见 2.5 联动分析）
- 两者不存在真正的阻塞依赖，可并行推进

### 6.4 实施要点

在 `phase-03.md` 的 step-1-explore 定义中，一步到位写成条件逻辑：

```markdown
### step-1.1 意图消歧
策略（按优先级尝试）：
1. 若 references/specs/L1-overview.md 存在 → 读取（~2K token）
2. 否则 → 读取 references/specs/ 下 4 个文件（~14KB），人工锁定 2-3 个候选模块

### step-1.2 模块定位
策略（按优先级尝试）：
1. 若 references/specs/L2-modules/{module}.md 存在 → 读取对应 L2 wiki
2. 否则 → list_dir 候选模块的前后端目录，确认文件清单
```

零改造代价：写一个模块的 L2 就立即生效一个模块。

### 6.5 探索即生成：自动生长知识库（2026-07-28 补充）

> 策略模式解决了"没有 L1/L2 时能跑"，但没有解决"跨项目迁移后知识库如何从无到有"。
> 本节补全这条链路——让知识库在迭代过程中自动生长。

#### 6.5.1 触发时机

在 03 阶段 step-1 探索完成后（回退路径走完），增加可选步骤：

```
### step-1.6（建议新增）知识库缓存
> ⚠️ 本步骤为方案提议编号，当前 phase-03.md/phase-steps.md 中不存在。
>   实施 S2 时需将 step-1.6 同步写入 phase-03.md 和 phase-steps.md 的步骤清单。

探索完成后，若 references/specs/L1-overview.md 不存在，自动生成之。
生成逻辑：
  1. 从本次探索的 list_dir + 已有 specs/ 文件中提取模块清单
  2. 按后端/前端分层，每行：模块名 | 职责（从 spec 描述提取） | 关键路径

| 风险 | 防护 |

### 6.6 批量生成模式：项目接入时一次性建 L1（2026-07-28 补充）

> 6.5 解决了"迭代中自动生长"，但新项目接入时，用户可能希望**先建好 L1 再开始迭代**，而不是等着第一次探索慢慢生成。
> 更关键的是——新项目**没有 4 个 specs 文件**作为数据源，6.5 的回退路径（`specs 全量 → list_dir`）从何谈起？

#### 6.6.1 数据源层级：specs 不是唯一来源

L1 的本质是"模块清单 + 目录映射"，可从多层数据源合成：

```
L1-overview.md
    ↑ 按优先级尝试以下数据源

① references/specs/ 4 文件（质量最高）
    → 从 API 端点 + Entity 清单 + 页面清单中提取模块名和职责
    → 质量：🟢 高（职责/路径详细）

② 项目根 README.md / docs/（质量中等）
    → 从已有文档提取模块描述
    → 质量：🟡 中（有人类维护的描述，但可能不完整）

③ 目录结构扫描（质量最低但任何项目都有）
    → list_dir 关键目录（BLL/ + pages/）→ 从目录名推断模块
    → 质量：🟡 中低（模块名准，职责靠命名推断，路径准）
```

#### 6.6.2 触发方式：独立命令入口

在 SKILL.md 中提供轻量级命令，不依赖活跃迭代：

```
命令：生成 L1 知识库 / gen-l1 / 建知识库总览 / init-knowledge-base

执行流程：
  Step 1. 探测可用数据源（按 6.6.1 层级逐级尝试）
  Step 2. 从最高优先级数据源提取模块清单
  Step 3. 合成 L1-overview.md，标记 confidence 等级
  Step 4. 写入 references/specs/L1-overview.md
  Step 5. 输出摘要：N 后端模块 + M 前端模块，置信度 {high|medium|low}
```

```

  1. 读当前 L1
  2. 用本次探索的发现更新职责描述（去掉 [推断] 标记）
  3. 提升 confidence: medium → high
  4. 补充新发现的模块
```

                                              ↓
                         step-1.6 变体 → 更新 L1（confidence→high）
                                              ↓
                         后续迭代 → 直接享受 L1 加速
```

### 6.7 L1 三模式统一关系（2026-07-28 审查修正）

> 6.5（探索即生成）、6.6（批量生成）、7.4.1（迭代开始目录对比）三处分别描述了 L1 的生成/更新方式。
> 以下明确三者的关系——它们是同一机制在不同场景下的触发入口，而非三个独立方案。

```
                      ┌─────────────────────┐
                      │   L1-overview.md    │
                      │   references/specs/ │
                      └─────────┬───────────┘
                                │
        ┌───────────────────────┼───────────────────────┐
        ↓                       ↓                       ↓
   ┌─────────┐           ┌───────────┐           ┌───────────┐
   │ gen-l1  │           │ step-1.6  │           │ 7.4.1 比对│
   │ (6.6)   │           │ (6.5)     │           │ (维护)    │
   └────┬────┘           └─────┬─────┘           └─────┬─────┘
        │                      │                       │
   触发：用户主动命令      触发：03 探索完成后       触发：迭代开始时
   动作：创建/重建 L1       动作：首次自动创建 L1     动作：对比目录→建议更新
   覆盖：是（用户意图）     覆盖：仅当 L1 不存在      覆盖：否（仅报告差异）
   场景：项目接入/重建      场景：无 L1 时首次迭代    场景：每次迭代保鲜
```

| 模式 | 触发方 | 触发时机 | 覆盖策略 | 覆盖范围 |
|------|--------|---------|---------|---------|
| **gen-l1 命令**（6.6） | 用户主动 | 项目接入 / 重建 | 覆盖（用户意图） | 全量重建 |
| **step-1.6 自动生成**（6.5） | 03 探索流程 | 探索完成且 L1 不存在 | 仅当 L1 不存在 | 首次创建 |
| **7.4.1 目录比对**（7.4） | 迭代开始 | 每次迭代开始时 | 不覆盖（仅报告差异） | 差异检测 |

**关键规则**：
- `auto-generated: true` 的 L1 → 可被 gen-l1 或 step-1.6 自动覆盖
- `auto-generated: false`（手动编辑后移除标记）的 L1 → **只能人工编辑**，Agent 仅输出建议
- 7.4.1 目录比对**永不自动覆盖** L1，仅输出差异报告并提示用户手动执行 gen-l1

### 6.8 过渡期新旧知识库并行策略（2026-07-28 审查补充）

> 在旧路径 `.codebuddy/specs/`（4 个平铺 spec）迁移到新路径 `references/specs/`（L1+L2+L3 金字塔）期间，存在一个过渡窗口：新知识库部分就位，旧知识库仍然存在。Agent 需要知道"优先用哪个，什么时候可以删旧的"。

#### 6.8.1 三阶段过渡模型

```
阶段 1：双存（migration-in-progress）
  references/specs/ ← L1+L2 逐步建立（优先读取）
  .codebuddy/specs/ ← 4 文件保留不动（回退读取）
  Agent 行为：先试 references/specs/，失败则回退到 .codebuddy/specs/
  耗时：1-2 个迭代周期

阶段 2：单主（new-primary）
  references/specs/ ← 完整 L1+L2+L3（唯一数据源）
  .codebuddy/specs/ ← 标记废弃（README.md 说明），文件保留但不更新
  Agent 行为：只读 references/specs/，旧路径不加载
  耗时：确认阶段 1 稳定后执行

阶段 3：清理（cleanup）
  references/specs/ ← 唯一数据源
  .codebuddy/specs/ ← 已删除 4 个 spec 文件（或整个目录清空）
  MEMORY.md 中 `specs/` 引用全部更新为 `references/specs/`
```

#### 6.8.2 Agent 加载决策树

```
Skill 启动 → 检查 config.specs_dir（见 4.2）
  ├─ references/specs/L1-overview.md 存在 → 使用新知识库（阶段 2/3）
  │   └─ 需要 L2 时 → 读 references/specs/L2-modules/{module}.md
  │       └─ L2 不存在 → 回退到旧路径（阶段 1）
  │
  └─ references/specs/L1-overview.md 不存在 → 回退到旧路径（阶段 1）
      └─ .codebuddy/specs/ 文件是否存在？
          ├─ 是 → 读 4 个 spec 文件
          └─ 否 → 走 6.6.1 目录扫描（纯新项目）
```

#### 6.8.3 双存期间的数据一致性

| 风险 | 场景 | 防护 |
|------|------|------|
| 新旧数据不一致 | 旧 spec 已更新，新 L2 未同步 | 06 归档阶段同时检查新旧两套知识库是否一致，输出差异 |
| Agent 读了旧数据 | `references/specs/` 某 L2 缺失，Agent 回退到旧 spec | 回退时标注 `[data-source: legacy-specs]`，让用户知道数据来自旧源 |
| 删除旧文件过早 | 新 L2 还没写完就删了旧 spec | 阶段 1→2 转换需通过 06 归档检查（新 L2 覆盖率 >80% 才能进阶段 2） |

#### 6.8.4 与现有 MEMORY.md specs 引用的联动

MEMORY.md 中现有引用 `.codebuddy/specs/` 的地方（Spec 活文档路径），需在阶段 3 时统一更新为 `references/specs/`。更新清单：

| MEMORY.md 位置 | 更新内容 |
|---------------|---------|
| Spec 活文档路径描述 | `.codebuddy/specs/` → `references/specs/` |
| 前端调用链 spec 引用 | 同上 |
| 后端 Entity/API spec 引用 | 同上 |

> 此更新在 S1 的 `gen-l1` 执行后、阶段 2 转换前完成。

## 七、知识库维护策略：建完之后如何保鲜（2026-07-28 补充）

> 第四章确定了"知识库放哪"（`references/specs/`），第六章解决了"如何生成"（自动生长 + 批量生成）。
> 但缺少最关键的一环：**项目迭代后会修改大量文件，知识库如何跟上代码变更而不脱节？**
>
> 不解决维护问题，知识库就是一次性产物——建成那天开始贬值。

### 7.1 参照标杆：mailplugin 的 pre-commit 阻断体系

文章 5.2 节描述了 mailplugin 的维护机制——核心不是"定期整理"，而是**把维护变成不可跳过的强制步骤**：

```
代码变更 → git commit → pre-commit hook 触发
                              ↓
                    check_project_wiki_stale.py
                              ↓
              对比 .review_cache.json（SHA 基线）
                              ↓
              ┌──────┴──────┐
            有差异          无差异
              ↓               ↓
        退出码 1          退出码 0
        阻止提交          允许提交
        输出三色清单
        （新增/删除/大改）
```

四个协同组件：

| 组件 | 作用 |
|------|------|
| `.review_cache.json` | 记录每个文件上次审阅时的 SHA 基线 |
| `check_project_wiki_stale.py` | 对比代码 SHA 与基线，输出三色分诊清单 |
| pre-commit hook | 退出码 1 = 阻止提交，强制开发者顺手更新 wiki |
| 元数据驱动 overview | 改 `<module>.md` 的 desc 后 overview.md 自动跟随 |

**效果**：半年净增 200+ 文件、改动 1000+ 处，知识库零脱节。

### 7.2 直接迁移的障碍

| | mailplugin（iOS） | 本项目环境（.NET + Vue + SVN） |
|---|---|---|
| 版本控制 | Git，hook 原生支持 | SVN，**无 pre-commit hook 机制** |
| SHA 基线 | 文件级 SHA（git 原生） | SVN 有 checksum 但机制不同，实现成本高 |
| 开发者习惯 | 团队统一用 git + hook | SVN 用户无 hook 习惯，强行推阻力大 |
| 门禁载体 | git hook（操作系统级） | CodeBuddy IDE 不支持 PreToolUse Hook（P-041） |

**结论**：核心思路（强制性 + 自动化 + 三色分诊）完全可借鉴，但**实现方式需要因地制宜**。

### 7.3 行业维护策略汇总

除了 mailplugin 的 pre-commit 阻断，行业里还有几种主流做法：

#### 策略 A：分层维护（最务实）

| 层级 | 触发方式 | 强制力 | 适用场景 |
|------|---------|--------|---------|
| **硬阻断** | 06-归档阶段强制检查（不改完不给归档） | ★★★ 强 | 我们已有，可直接扩展 |
| **软提醒** | CI/构建阶段 advisory 报告 | ★★☆ 中 | 可新增 |
| **懒更新** | 下次探索时发现不一致 → 自动更正 | ★☆☆ 弱 | 已通过 6.5 探索即生成解决 |

#### 策略 B：代码即文档（Code-as-Docs）

从代码注释中自动提取模块元数据，而非反向生成：

```csharp
// @module: TriageAssessment
// @desc: 预检分诊评估主流程（分级判定/信息采集/绿通触发）
// @api: POST /webapi/TriageAssessment/SaveAssessment
public class TriageAssessmentBLL { ... }
```

脚本扫描 `@module`/`@desc`/`@api` → 自动更新 L1/L2。**最理想但改造成本高**（需全项目加注释）。

#### 策略 C：机器人巡检（Cron + Report）

利用现有 automation 机制，定时扫描变更：

```
每周一自动执行：
  svn log -r {上次检查日期}:HEAD → 变更文件列表
  对比 L2 模块 wiki 的 root_dirs → 发现新增/删除目录
  输出：⚠️ 以下模块可能过时：TriageAssessment (2文件变更), GreenChannel (新增目录)
```

不阻断但可见，积压到一定程度提醒人工介入。

#### 策略 D：目录即真理（Directory-as-Source）

L1 的 `root_dirs` 不靠手工维护，靠脚本从实际目录结构自动生成。只要约定"目录名 = 模块名"，L1 就永远不会过时。

```python
# 每次迭代开始前自动执行
for dir in list_dir("BLL/"):
    modules.append({"name": dir, "path": f"BLL/{dir}/"})
```

L1 最不容易过时的方式——目录结构是代码的一部分，开发者改代码自然会改目录。

### 7.4 适配方案：三层维护体系

结合以上分析和我们的实际约束（SVN、无 hook），推荐组合策略：

```
第一层：目录即真理（防 L1 过时）
  └→ L1 的模块列表从目录结构 scan 生成，不手工录入
  └→ 目录变更 → L1 自动跟随，零维护成本

第二层：06-归档硬阻断（防 L2 过时）
  └→ 归档阶段强制检查：本次迭代修改的文件是否都在对应 L2 wiki 中
  └→ 新增/删除/大改文件 → 强制更新 L2 wiki 后才能归档
  └→ 输出三色清单（对标 mailplugin 的分诊理念）

第三层：周期性巡检 automation（防遗漏）
  └→ 每周一自动扫 SVN log + 对比 L2 root_dirs
  └→ 生成 advisory 报告，不阻断但可见
  └→ 积压到阈值时提醒人工介入
```

#### 7.4.1 第一层实现：L1 目录扫描自动生成

已经在 6.6 中实现——`gen-l1` 命令的核心就是目录扫描。每次执行 `gen-l1` 都从最新目录结构重新生成，不存在"过时"问题。

但需要增加一个机制：**迭代开始时自动比对**——

```
迭代开始（01 或 03 阶段）：
  1. scan 当前后端 BLL/ 目录 + 前端 pages/ 目录
  2. 对比 references/specs/L1-overview.md 中记录的模块列表
  3. 输出差异：
     + Added: GreenChannelV2 (新目录)
     - Removed: OldModule (目录已删除)
     ~ Changed: TriageQueue (文件数变化: 12→15)
  4. 差异 > 0 → 提醒用户执行 gen-l1 更新
```

此检查耗时 <2 秒（仅 `list_dir` 两次），token 消耗 <1K。

#### 7.4.2 第二层实现：06-归档 L2 硬阻断

在 `phase-06.md` 中增加检查项：

```markdown
### 归档前知识库检查（新增）

1. 列出本次迭代涉及的所有变更文件（从任务清单 + commit diff）
2. 对每个变更文件，确认其所属模块的 L2 wiki 已更新：
   - 若文件路径在 L2 wiki 的 root_dirs 中 → 检查 L2 wiki 的文件列表是否包含此文件
   - 若为新增文件 → 检查 L2 wiki 是否已登记
   - 若为删除文件 → 检查 L2 wiki 是否已移除
3. 输出三色清单：
   🟢 已同步：12 个文件（L2 wiki 已反映变更）
   🟡 需确认：3 个文件（L2 wiki 存在但路径可能不对）
   🔴 缺失：  2 个文件（L2 wiki 未登记，请补全后重新归档）
4. 🔴 清单非空 → 阻止归档，强制补全
```

这与现有 06 归档的 Spec 更新逻辑一脉相承，只是把检查颗粒度从"整个 spec 文件"细化到"每个模块的 L2 wiki"。

#### 7.4.3 第三层实现：周期性巡检

利用 CodeBuddy automation 机制，配置周度巡检：

```
automation: knowledge-base-health-check
schedule: 每周一 09:00
prompt: |
  1. 读取 references/specs/L1-overview.md 获取模块列表
  2. list_dir 后端 BLL/ 和前端 pages/ 目录
  3. 对比差异：新增/删除/重命名的模块
  4. 对每个 L2 存在的模块，检查 root_dirs 中的路径是否仍存在
  5. 生成健康报告，若有 🔴 项则 @用户
```

> ⚠️ **平台依赖风险**：此方案依赖 CodeBuddy IDE 的 automation 功能。若项目寄宿在其他 IDE（如 Cursor、VS Code + Claude Code），需替换为对应工具的定时任务机制（如 cron job 调用 CLI agent）。**不能假设 automation 在所有环境中都可用**。降级方案：将巡检逻辑嵌入 01/03 阶段开始时（每次迭代自动触发），而非依赖独立定时任务。

#### 7.4.4 L3 语义桥的维护策略

> 7.4 的三层维护体系覆盖了 L1（目录扫描）和 L2（归档阻断），但 L3 语义桥同样会脱节——新增的 API、改名的方法、新增的业务术语都不会自动进入 L3。

L3 的维护触发点：

| 场景 | 触发 | 动作 |
|------|------|------|
| 新增 API/方法 | 06 归档 L2 硬阻断时顺便检查 | 新 API 名称+路由→L3 新增一行；新业务术语→L3 新增一行 |
| 更名 | 06 归档 L2 硬阻断时 | 旧名称标记删除线 `~~old~~`，新名称新增一行（保留旧名3个迭代周期后清理） |
| 发现术语缺失 | 03 探索时（漏斗 Step 3 用 L3 扩展搜索词） | 若某个搜索词在 L3 中找不到 → 标记 `[TODO: add to L3]`，06 归档时补全 |
| 手工清理 | 用户主动 | 删除已弃用的术语行（距标记删除超过 3 个迭代周期） |

L3 维护成本极低（每次迭代 2-5 分钟），因为大部分术语变更会在 06 归档时自然暴露。

### 7.5 维护成本对比

| 场景 | 无维护机制 | 采用三层体系 |
|------|-----------|------------|
| 新增一个后端 BLL 模块 | L1/L2/L3 永久缺失该模块 | 下次 `gen-l1` 自动发现（L1），06 归档时强制登记（L2），API 术语自动入库（L3） |
| 删除一个前端页面 | L1/L2 残留死链接，L3 残留废弃术语 | 迭代开始时目录对比告警 → gen-l1 更新，L3 术语标记删除 |
| 重构：文件从 A 模块移到 B 模块 | L2 两个模块都不对 | 06 归档三色清单标红，强制更新 |
| 新增 API 端点 | L3 语义桥搜索词不可命中 | 06 归档时 L2 更新自然带动 L3 补全 |
| 6 个月不做任何维护 | 知识库完全脱节，定位漏斗退化 | 周巡检持续报警，问题不会被遗忘 |

### 7.6 与其他章节的联动

| 关联章节 | 联动点 |
|---------|--------|
| 6.5 探索即生成 | 第一层维护（迭代开始时 L1→目录 对比）的触发方 |
| 6.6 批量生成 | `gen-l1` 同时是维护工具——任何时候执行都会更新 L1 |
| 6.7 L1 三模式统一 | 维护层（7.4.1）是 gen-l1/step-1.6 之外第三种触发入口 |
| 6.8 过渡期并行 | 双存期间维护需同时检查新旧两套知识库一致性 |
| 4.1 外部路径风险 | 知识库在 `references/specs/` 内 → 维护脚本路径稳定 |
| 4.2 specs_dir 配置 | 引擎通过配置变量定位知识库，维护脚本复用同一路径 |
| 06-归档阶段 | 第二层硬阻断的落地位置 |
| 08-01阶段使用 | 01 阶段通过 L1 快速锁定模块范围，减少 token 消耗 |
| 第九章借鉴方案 | 9.6 联动总图：01(grill-with-docs)→03(漏斗)→04(Superpowers模板)→05(合规检查)→06(归档保鲜) |

### 7.7 实施优先级

| 层级 | 实施难度 | 价值 | 建议顺序 |

| 第三层（周巡检） | 低（已有 automation） | 中（查漏补缺，但有平台依赖） | **第三步** |

## 八、01-需求分析阶段如何使用知识库（2026-07-28 审查补充）

> 前面章节聚焦于 03（技术方案探索）和 06（归档维护），但 01-需求分析与设计 阶段同样是知识库的重要消费方。
> 在需求分析阶段，Agent 需要理解"改什么模块、影响哪些文件"——这正是 L1+L3 发挥价值的地方。

### 8.1 01 阶段的知识库使用场景

| 子步骤 | 当前做法 | 改进后（有知识库） |
|--------|---------|-------------------|
| 理解需求范围 | Agent 凭经验猜测涉及哪些模块 | 读 L1 总览 → 直接锁定 1-3 个候选模块 |
| 需求→模块映射 | 用户手动告知"这个需求改 X 模块" | L1 提供模块清单 + 职责描述，Agent 可独立判断 |
| 术语消歧 | Agent 猜测命名（可能猜错） | L3 语义桥提供准确的代码命名，避免需求文档用词与代码不一致 |
| 影响范围估算 | 无依据的粗略估计 | 读候选模块的 L2 wiki → 知道涉及多少文件，输出准确的复杂度评估 |
| 设计文档生成 | 手写模块名/路径 | L1+L2 可自动填充设计文档中的"涉及模块""文件清单"部分 |

### 8.2 01 阶段的加载策略（极简）

与 03 的五步漏斗不同，01 只需要前三层信息：

```
01 阶段启动 → 加载 L1-overview.md（~3K token）
  ↓
需求理解完成 → 读候选模块 L2 wiki 的 root_dirs（只看路径，不读文件清单）
  ↓
术语确认 → 查 L3-glossary.md（按需，~1K token）
```

**Token 消耗**：01 阶段额外消耗 <5K token（L13K + L3 按需），远低于当前无索引时的全量 specs 加载。

### 8.3 与现有迭代引擎的集成点

在 `phase-01.md` 的 step-2（需求理解/范围界定）中扩展：

```markdown
### step-2.1（新增）模块范围定位

利用 L1 总览，将用户需求映射到具体模块。若无 L1，回退到现有做法（用户显式告知）。

策略（按优先级尝试）：
1. 若 references/specs/L1-overview.md 存在 → 读取，输出候选模块清单
2. 否则 → 跳过，由用户显式告知涉及模块
```

> **复杂度**：改动量极小，仅在 `phase-01.md` 增加一个可选步骤，与 6.4 三步联动相同模式。

## 九、Superpowers + grill-with-docs 借鉴方案（2026-07-28 对标研究）

> 前八章聚焦 `mailplugin-feature-dev` 的知识库分层和代码定位漏斗。本章补充两个高 star 开源项目的可借鉴点：
> - **obra/superpowers**（~200K stars，680K+ 安装量）：7 步强约束开发工作流
> - **mattpocock/skills** 中的 **grill-with-docs**（~123K stars）：需求对齐 + 共享语言注入

### 9.1 Superpowers 7 步工作流 → iteration-workflow 差距分析

| Superpowers 步骤 | iteration-workflow 对应阶段 | 差距 | 借鉴方向 |
|------------------|---------------------------|------|---------|
| 1. brainstorming（苏格拉底提问打磨设计） | 01 需求分析 | 01 是"读需求→分析"，缺失主动追问 | **9.4.1** 01 增加闭环追问步骤 |
| 2. using-git-worktrees（隔离工作空间） | 无 | 无对应机制，多 Story 并行缺少隔离 | 暂不借鉴（SVN 不支持 worktree） |
| 3. writing-plans（拆 2-5 分钟微任务，精确到文件路径+代码片段+验证步骤） | 04 任务清单 | 04 任务粒度粗（"新增分诊评估页"），缺文件路径+代码片段 | **9.4.2** 任务清单模板增加三列 |
| 4. subagent-driven-development（并发子代理 + 两级审查） | 04 Team Agent 模式 | 两级审查（规范合规→代码质量）缺失 | **9.4.3** 05 测试阶段加合规检查子步骤 |
| 5. TDD（红→绿→重构，测试不通过禁止继续） | 05 测试验证 | 05 是"写完再测"，无硬阻断 | **9.4.4** 04→05 加 TDD 硬阻断 |
| 6. requesting-code-review（对照计划逐项审查） | 评审双层清单 | 评审已较成熟，但缺少"对照计划自动逐项 check" | **9.4.5** 评审对照任务清单自动化 |
| 7. finishing-a-development-branch（合并/PR/丢弃决策） | 06 归档 | 06 归档步骤粗粒度，缺少分支收尾决策 | 暂不借鉴（SVN 无 PR 机制） |

**核心差异总结**：

| 维度 | Superpowers | iteration-workflow | 
|------|------------|-------------------|
| 约束力 | **强约束**——技能加载后变成强制性流程，Agent 不能跳过 | **引导式**——阶段定义完整，但 Agent 有自主解释空间 |
| 任务粒度 | 2-5 分钟微任务，含精确文件路径+代码片段+验证步骤 | 粗粒度任务（"实现 XX 功能"），依赖 Agent 自行拆分 |
| 质量关卡 | TDD 硬阻断 + 两级审查 | 评审双层清单（软性），测试无强制流程 |
| 隔离性 | git worktree 分支隔离 | 多 Story 并行但同一工作区 |

### 9.2 grill-with-docs 核心机制：盘问 + 共享语言 + 即时写入

```
grill-with-docs 三步法：

  Step 1: 穷举式盘问（grilling）
    └→ 把所有模糊计划和设计决策的分支逼问清楚
    └→ 不是"读完需求就过"，而是"追问直到穷举所有可能性"

  Step 2: 构建共享语言（Ubiquitous Language）
    └→ 识别并提炼领域术语
    └→ 将用户的业务用词与代码命名对齐

  Step 3: 即时写入仓库
    └→ CONTEXT.md：项目术语表和领域知识库
    └→ ADR（架构决策记录）：难以简化的决策
    └→ 后续会话直接继承，一劳永逸
```

**与现有 L3 语义桥的差异**：

| | L3 语义桥（现有） | grill-with-docs 共享语言 |
|---|---|---|
| 建立时机 | 06 归档时补全（事后） | **01 需求对齐时建立（事前）** |
| 内容 | 业务术语→代码命名 映射表 | 业务术语 + 领域模型 + 设计决策 |
| 写入目标 | `L3-glossary.md` | `CONTEXT.md` + ADR（项目根文件） |
| 后续会话 | 按需加载 L3 | **自动加载 CONTEXT.md**（Agent 启动即读取） |

### 9.3 联合效应：为什么两者一起借鉴效果最好

```
grill-with-docs（01阶段加固）
  └→ 需求理解准确 + 共享语言注入 CONTEXT.md
        ↓
Superpowers writing-plans（04阶段加固）
  └→ 基于准确的共享语言，任务拆分到文件路径+代码片段级
        ↓
Superpowers TDD + subagent 两级审查（04→05质量拦截）
  └→ 每个微任务先写测试→再实现→合规检查→代码审查
        ↓
06归档
  └→ L2 wiki 更新 + L3 语义桥从 CONTEXT.md 同步过来
```

**效果预估**：

| 指标 | 当前 | 借鉴后 |
|------|------|--------|
| 需求理解准确率 | ~70%（依赖 Agent 经验） | ~90%（穷举追问 + 共享语言对齐） |
| 04 任务清单准确度 | ~60%（粗粒度，Agent 自行发挥） | ~85%（精确到文件路径 + 代码片段） |
| 回归率（新功能引入 bug） | ~15% | ~5%（TDD 硬阻断 + 两级审查） |
| 知识库时效性 | 06 归档才更新（滞后 1 个迭代） | 01 就开始建立（提前 5 个阶段） |

## 十、验收方案：如何证明改进有效

> 前九章定义了"改什么"和"怎么改"，本章定义"怎么算改好了"。
> 验收框架分三层：**单元验收**（每个 S 阶段独立指标）、**集成验收**（跨阶段联动效果）、**端到端验收**（真实迭代对比）。

### 10.1 验收框架总览

```
单元验收（每个 S 阶段完成后）
  └→ 产出物是否存在 + 格式是否正确 + 内容是否达标
        ↓
集成验收（S1+S2 联调后）
  └→ L1/L2 是否能驱动漏斗 Step 1-2 正确收敛
        ↓
端到端验收（一个完整迭代跑完后）
  └→ Before/After 定量对比：Token、时间、命中率、回归率
```

**验收时机**：

| 验收层级 | 触发时机 | 谁做 | 耗时 |
|---------|---------|------|------|
| 单元验收 | S1~S4 每阶段完成后 | Agent 自查 + 用户确认 | 5-10 分钟/阶段 |
| 集成验收 | S1 和 S2 都完成后 | 跑一次完整 03 探索 | 15-20 分钟 |
| 端到端验收 | 模拟一个完整迭代（01→06） | Agent + 用户联合 | 1-2 小时 |

| E4 | 04 任务清单文件路径准确率 | 任务清单中文件路径与实际修改文件一致的比例 | 无此列(NA) | **≥ 90%** | 对比任务清单 vs 实际 commit |
| E5 | 归档 L2 更新遗漏率 | 06 归档时发现 L2 未更新的文件数 / 总变更文件数 | 无此检查(NA) | **< 10%** | 06 归档三色清单 |
| E6 | 01 闭环追问覆盖率 | 追问的问题数 / 需求中的模糊点总数 | 0（无此步骤） | **≥ 80%** | 01 step-2.2 追问清单 |
| E7 | 规范合规错误率 | 05 step-1.5 拦截的规范违反数 / 总变更数 | 无此检查(NA) | 首次发现后修复率 100% | 05 合规检查清单 |

#### 10.3.2 辅助定性指标（观察性，不设硬阈值）

| # | 指标 | 观察方式 |
|---|------|---------|
| E8 | 知识库覆盖率 | 迭代后 L1/L2 中是否存在本次未涉及的模块描述错误 |
| E9 | 术语一致性 | 01 阶段记录的术语是否与 04 实现的代码命名一致 |
| E10 | CONTEXT.md 活跃度 | 历经 2 个迭代后 CONTEXT.md 是否有新增/更新行 |
| E11 | 回退路径触发频率 | 统计 L2 未命中导致走 `list_dir` 回退的次数（越低越好） |
| E12 | 用户介入次数 | 01 闭环追问你回答了多少个问题（反映需求模糊度，不是故障） |

### 10.4 端到端验收的测试需求选取原则

验证用的需求应满足以下条件（**不能选太简单或太特殊的需求**）：

| 原则 | 说明 |
|------|------|
| **中等复杂度** | 涉及 2-3 个模块，前后端都有改动 |
| **含新文件** | 至少新增 1 个文件（检验 L2 登记、.csproj 检查、06 硬阻断） |
| **含跨模块调用** | 至少一个修改涉及跨 BLL 调用（检验漏斗 Step 4 调用链追踪） |
| **含数据库变更** | 涉及建表或改表（检验表名全大写检查） |
| **含前端 UI + 逻辑** | 不纯后端或纯前端（检验 L3 语义桥前端维度） |

**推荐测试需求示例**（从预检分诊项目选取）：

> "分诊评估页新增'转科建议'功能，分诊完成后可录入建议转诊科室。前端新增下拉选择 + 提交按钮，后端新增 TRANSFER_SUGGESTION 表 + 保存/查询 API，BLL 需校验分诊级别为 I/II 级才能建议转科。"

这个需求覆盖：新表（Entity 大写 + .csproj）、新 API（路由注册）、前端 UI+逻辑、跨模块校验（TriageAssessment → TransferSuggestion）。

### 10.5 数据收集方案

#### 10.5.1 基线数据收集（改进前）

在实施任何改动前，跑一次当前流程作为基线：

```
操作：
1. 在 test 分支执行一次完整的 03 step-1 探索（随便一个需求）
2. 记录：
   - 使用的 tool calls 列表（code-explorer / search_content / read_file）
   - 每次 tool call 的输入输出 token（从 Agent 日志估算）
   - 从开始探索到锁定所有改动文件的时间
   - 搜索命中的文件数 vs 最终实际需要的文件数
3. 保存基线数据到 S2 验收记录

注意：基线数据不需要在 S1 实施前收集，可以在 S2 实施前收集作为"改进前对照"
```

#### 10.5.2 改进后数据收集

在 S2 实施完成后，用同一需求（或等价需求）再跑一次：

```
操作：
1. 确保 L1 + 核心 L2 已就位（S1 验收通过）
2. 确保 S2 五步漏斗已部署
3. 跑同一个需求的 03 step-1 探索
4. 记录与 10.5.1 相同的指标
5. 对比 E1~E3
```

#### 10.5.3 端到端数据收集

在 S1+S2+S3+S4 全部完成后：

```
操作：
1. 用 10.4 推荐的测试需求
2. 从 01 阶段开始完整跑一遍 01→02→03→04→05→06
3. 在每个阶段记录对应指标（E1~E7）
4. 输出端到端验收报告
```

**数据记录模板**：

```markdown

### 10.6 验收通过标准汇总

| 层级 | 条件 | 不满足时的处理 |
|------|------|-------------|
| **S1 单元** | 10 项全部 ✅ | 修复未达标的项目后重新验收 |
| **S2 单元** | 6 项全部 ✅ | 修复后重新验收；若仅 S2-03（Token 边界）差，记录为 ⚠️ 可继续 |
| **S3 单元** | 4 项全部 ✅ | 补全缺失的 L2/L3 后重新验收 |
| **S4 单元** | S4-01~03 必须 ✅，04/05 可 ⚠️ | 核心三项不通过则修复后重验 |
| **集成** | 四种场景（理想/半建/空白/异常）全部正确 | 修复回退逻辑后重验 |
| **端到端 E1~E7** | ≥5/7 达标，且 E1（Token）必须达标 | E1 不达标 = 不通过；其余可降级为 ⚠️ 记录改进计划 |
| **最终裁定** | S1+S2+S3+S4 单元全通过 + 集成全通过 + E1 达标 | — |

### 10.7 验收失败的回滚机制

```
验收不通过 → 分情况处理：
 
  ① S1 产出物质量不达标（如 L2 路径写错）
     → 直接在迭代中修正，不涉及回滚引擎代码
 
  ② S2 漏斗流程有问题（如 step-1.2 回退死循环）
     → 回滚 phase-03.md 的改动，修复后重新部署
 
  ③ 端到端 E1 Token 反而增加
     → 检查 L1/L2 是否加载了冗余内容（如 L2 文件太大）
     → 检查搜索词是否因 L3 过度扩展导致噪声增加
     → 针对性优化后重新测试
 
  ④ 集成测试四种场景有两种以上失败
     → 回滚 S2，保持现有 code-explorer 方式
     → S1 知识库保留（仍有独立价值），S2 延期到修复后
```

### 10.8 实施顺序与验收互锁

```
实施 S1 → 单元验收 S1 ✅
   ↓
实施 S2 → 单元验收 S2 ✅ → 收集基线数据 → 集成验收 ✅
   ↓
实施 S3 → 单元验收 S3 ✅
   ↓
实施 S4 → 单元验收 S4 ✅
   ↓
全量就位 → 端到端验收（跑完整迭代）→ 最终裁定
```

**关键约束**：端到端验收**不能跳过**。单元验收都过了 ≠ 整体有效。只有用真实需求跑完 01→06 全流程，才能验证跨阶段联动是否真的产生了 1+1>2 的效果。

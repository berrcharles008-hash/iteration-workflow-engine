## 二、可靠性（Robustness / Gate Enforcement）

**评估方向**：门禁体系的严密性、能否被绕过、门禁失败后的恢复路径。

### 2.1 三层门禁独立性

| 门禁 | 触发性 | 独立性 |
|:----:|:------:|:------:|
| 修改门禁 | 🟢 准备写入类工具时 | 🟢 独立于其他门禁 |
| 迭代门禁 | 🟢 用户请求"新迭代"时 | 🟢 独立于其他门禁 |
| 步骤门禁 | 🟢 条件重武装触发时 | 🟢 独立于其他门禁 |

**优秀点**：三层门禁彼此不依赖，架构设计合理。

### 2.2 门禁绕过风险分析

| 潜在绕过路径 | 风险等级 | 说明 |
|------------|:-------:|------|
| **非标准触发词绕过** | 🔴 **已发生事故** | CLAUDE.md 记录 2026-07-15："'开始实施'不在 Skill 触发词列表中导致门禁被绕过"。**修复方式仅为追加"开始实施"到触发词列表——这是黑名单模式的固有缺陷**：漏掉一个词就是一次绕过，补词只是事后修补 |
| 用户直接给出 `replace_in_file` 内容 | 🟡 有条件绕过 | 门禁依赖 Agent 先判断"准备调用写入工具"。若用户直接说出具体代码且 Agent 未进入门禁流程即执行，则绕过。SKILL.md 的"轻量查询快速退出"判断先于门禁执行——若用户意图被误判为"状态查询"（如"看看当前进度，顺便改一下 label"），则门禁不会触发 |
| 门禁豁免列表 | 🟡 需审查 | 修改 Skill 自身文件豁免（gate-protocol.md §四）——自行修改 gate-protocol.md 时无门禁保护。参考独立评审"演化健壮性"问题 |
| 06→07 阶段推进 | 🟢 安全 | 三-B 确认门禁豁免，但三-C 结清门禁仍在 |
| ACTIVE 失同步 | 🟡 有隐患 | 有兜底扫描 + 自修复机制。但兜底扫描逻辑含分支路径（损坏/不存在 走不同路径），**不同分支行为不一致 = 非确定性 fallback**。实际效果依赖 Agent 是否正确判断 |

### 2.3 阶段推进门禁的三重检查

```
准备推进 current_phase：
  ├── §三-A 评审门禁：检查 review_gate.result（02/03 阶段）
  ├── §三-B 确认门禁：检查用户本轮指令含通过语（任何阶段，06→07豁免）
  └── §三-C 结清门禁：检查 mandatory 步骤均已 completed/skipped（任何阶段）
```

**评价**：🟢 三重检查互不重叠。但三-B 的"含通过语"依赖关键词匹配——Agent 对"没问题"和"还行，继续"的判断是否一致无测试保障。

### 2.4 Agent 长对话行为漂移（新增）

> **根因**：门禁规则仅存在于 prompt 上下文中。当对话超过 20+ 轮后，上下文压缩机制可能剪掉 gate-protocol.md 关键段落。

| 风险 | 场景 | 防护 |
|:----:|------|:----:|
| 门禁遗忘 | "之前确认过，改一下吧"——Agent 记忆中有确认句，但门禁规则已被压缩 | ❌ 无——门禁是 prompt 软约束，非编译期硬约束 |
| 步骤门禁条件重武装失效 | 条件重武装的前提是 Agent 能"自检"——上下文压缩后自检也可能被跳过 | ❌ 无 |
| ACTIVE 读取错误 | 压缩后 Agent 可能误记当前迭代ID或状态 | ❌ 无 |

**建议**：将门禁核心规则写入 CLAUDE.md（项目级常驻指令，不被压缩）或 runtime/ 级的可执行约束。

### 🟡 可靠性待改进项

1. **白名单模式替代黑名单**：不应依赖"触发词列表涵盖了所有表达"，应改为"非明确授权操作→走门禁检查"
2. **长对话行为漂移无防护**：核心规则应写入 CLAUDE.md 而非仅依赖 prompt
3. **ACTIVE fallback 非确定性**：多种损坏路径的行为不一致
4. **门禁规则无自动化测试**：无门禁检查的测试用例保障

## 七、安全性（Safety）

### 7.1 破坏性操作确认链

| 操作 | 确认级别 | 说明 |
|------|:-------:|------|
| 代码修改 | 🟢 三层门禁 | 修改门禁 + 迭代门禁 + 步骤门禁 |
| 阶段推进 | 🟢 三重检查 | 评审门禁 + 确认门禁 + 结清门禁 |
| 迭代删除 | 🟢 不可逆分级 | 已归档→不可删除，进行中→警告，暂停→警告 |
| 部署上线 | 🟢 明确确认 | 06 阶段需要用户确认"上线完成" |
| 归档 | 🟢 双重确认 | 06 归档 + 07 回顾归档 |

### 7.2 多工具/多会话并发（🔴 升级）

> 原报告评 🟡。**这是数据损坏风险，应评 🔴。**

| 场景 | 风险等级 | 说明 |
|:----:|:-------:|------|
| **两个 Claude Code 会话同时操作同一迭代** | 🔴 **数据损坏** | 两个会话分别读取 state.yaml → 各自修改状态字段 → 分别写入 → 后写入的覆盖先写入的。**无锁、无版本号、无冲突检测**。phase_steps、task_progress、last_session_summary 全部可能丢失 |
| Claude Code + CodeBuddy 同时操作 | 🔴 **数据损坏** | 同上——state.yaml 不是 DB，没有事务保证。core-rules.md 只规定了文件级同步策略，未规定写入锁定 |
| 用户手动编辑 state.yaml + Agent 自动写入 | 🟡 数据不一致 | 无文件级写入互斥。Agent 写入前不检查文件修改时间戳 |

**当前唯一防护**：靠人工协调"不同时使用"。这在"只有一个人的小团队"勉强可行，但不可靠。

### 7.3 敏感信息

- 🟢 外部模型 API Key 走环境变量（`api_key_env`），不硬编码
- 🟢 `review-models.json` 不纳入 Git 跟踪
- 🟡 **但无显式审计**：敏感信息是否写入日志/lessons-learned 的检查

### 🔴 安全性待改进项

1. **state.yaml 并发写入数据损坏风险**：需文件锁（如 `runtime/.lock`）+ 版本号检查（写入时对比读取时的版本号，不一致则冲突异常）
2. **无多工具/多会话互斥机制**
3. **未审计日志/memory/lessons-learned 中的敏感信息**

## 八、演化健壮性（Evolution Robustness）⭐ 新增维度

> 独立评审提出的第 8 维。评估 Skill 能否用自身流程可靠地修改自身——**自引用系统的核心问题**。

### 8.1 自引用循环分析

| 场景 | 风险评估 | 是否死锁 |
|:----:|---------|:-------:|
| 修改 gate-protocol.md → 需要先过当前门禁 → 当前门禁正是你在改的 | 🟡 逻辑矛盾 | **有条件死锁**——若修改涉及门禁触发条件（如增加/减少触发场景），当前检查的是旧规则还是新规则？ |
| 修改 SKILL.md 关键原则 #0（修改门禁）| 🟡 规则自我否定 | **逻辑矛盾**——用当前门禁去修改 "修改门禁" 本身 |
| 新增 04 阶段步骤 → 修改 workflow-engine.md + phase-steps.md | 🟢 无循环 | 新增步骤不改变现有门禁的行为，不会自引用 |
| 修改 complexity-scoring.md 的评分因素 | 🟢 无循环 | 复杂度评估是纯数据，不引用自身 |
| 修改 cross-review-protocol.md 的审查指令 | 🟢 无循环 | 审查指令不审查自身 |

**结论**：自引用循环**有条件存在**——聚焦于"门禁规则自身"的修改有逻辑矛盾，但修改"门禁触发后的行为"、各阶段执行步骤、模板文件等不受影响。

### 8.2 门禁豁免的安全隐患

gate-protocol.md §四 豁免了"修改 Skill 自身进化文件"——这意味着修改 gate-protocol.md 本身时也无门禁保护。这设计使 Skill 自我进化可行，但也意味着门禁的"不可绕过承诺"不适用于自身修改。

### 8.3 自我修复验证

lessons-learned.md P-021 记录了一次成功的自我修复迭代，验证了：
- ✅ Skill 自身定义的 7 阶段流程可用于修复 Skill 自身
- ✅ 05 阶段验证发现了 3 项遗漏并修复
- ✅ 用户的 05 用例审查比 Agent 自动审查更强

这是一个正向案例，证明自引用在实践中有闭环。

### 🟡 演化健壮性总结

- **门禁规则修改存在自引用逻辑矛盾**，但实际影响有限（user 在 loop 中可裁定）
- **自引用修改的历史案例（P-021）成功**，证明可行
- **建议**：当修改 gate-protocol.md 的 §一~§三（门禁规则）时，强制输出"本次修改对门禁行为的影响声明"

### ⚪ 未覆盖的演化场景

- **完全重写 Skill**：将 7 阶段流程改为 5 阶段时，现有流程无法承载"修改流程定义自身的流程"
- **多版本 Skill 迁移**：v1 → v2 时的 artifact 兼容性无定义

### 10.7 跨项目部署缺口与方案 E（P-045）

#### 10.7.1 问题：P-043 修复的静默部署依赖

P-043 的修复方案（冷启动门禁微核）将门禁逻辑写入项目的 `MEMORY.md`。这意味着：

```
iteration-workflow Skill ──安装──▶ 新项目
                                   │
                                   ├── SKILL.md / engine/ 等 ✅ 自动
                                   └── MEMORY.md 微核      ❌ 静默缺失
```

**后果**：Skill 安装到新项目后，`MEMORY.md` 不含微核 → 冷启动会话无门禁保护 → P-043 真空在新项目中复现。没有任何机制保证微核被自动部署。

#### 10.7.2 初始方案：A+B 组合

| 方案 | 思路 | 机制 |
|:--|:--|:--|
| **A** | Skill 首次加载时检测 MEMORY.md 是否含微核，无则 Agent 自动写入 | Prompt 层，Skill 生效后触发 |
| **B** | 提供 `setup-gate` 安装脚本，安装 Skill 后显式执行 | 脚本层，用户主动触发 |

#### 10.7.3 双审结果

| 审查方 | 结论 | 关键发现 |
|:--|:--|:--|
| 独立 Agent（对抗性审查） | ⚠️ 有条件通过 | 3 个阻塞项：鸡生蛋死锁（门禁拦截注入操作）、静默修改项目文件、版本同步缺失。推荐方案 E |
| 外部模型（Skill-Inject 论文，arXiv 2602.20156） | 🔴 高风险模式 | 方案 A 恰好命中论文核心攻击向量：Skill 静默修改项目文件，Agent 误判概率高，无用户权限校验 |

#### 10.7.4 环境感知洞察：微核是 CodeBuddy IDE 专属补丁

在方案修订过程中发现了一个关键认知盲区——A+B 方案和双审报告都默认了"微核方案对所有 IDE 有效"，但实际上：

| 环境 | 门禁方式 | 需要微核？ | MEMORY.md 存在？ |
|:--|:--|:--:|:--:|
| **CodeBuddy IDE** | Prompt 层（微核 + gate-protocol.md） | ✅ 需要 | ✅ `.codebuddy/memory/MEMORY.md` |
| **Claude Code CLI** | Hook 层（gate-check.mjs PreToolUse 硬拦截） | ❌ 不需要 | ❌ 无此机制 |

**核心结论**：冷启动微核是 CodeBuddy IDE 的专属补丁——因为 CodeBuddy IDE **不支持 PreToolUse Hook**（P-041 实测验证），必须用 Prompt 层兜底。Claude Code CLI 的 Hook 在工具调用层面直接硬拦截，不需要 Prompt 层微核。方案 E 必须感知运行环境，不能对所有 IDE 一刀切。

# 可选组件分发规范 v0.1

> 2026-10-28 · TOOL-QQBOT-DIST 收口产物。首个实例 = `qqbot`（QQ 通知通道）。
> 目的：以后再加可选组件（如 session-hub、外部审查模型配置器）时**直接套用**，不必重开一轮设计讨论。
> 判据侧（审计脚本）不引用本文件 —— 它属于实现说明，不是协议。

---

## 一、什么是「可选组件」

**默认不安装**、需要时才启用、且**携带可执行代码或有宿主级副作用**（常驻进程 / 自启 / 计划任务 / 端口）的附加能力。

与既有概念的分界：

| 概念 | 形态 | 例 |
|---|---|---|
| 引擎协议 | 纯文档与判定逻辑，装 skill 即生效 | `engine/gate-protocol.md` |
| 项目配置 | 一个 YAML（`project/project.manifest.yaml`） | `notifications.adapter` |
| **可选组件** | 一整个目录（代码 + 配置样例 + 安装器），且需宿主级登记 | `tools/qqbot` |

## 二、生态对照（为什么是这个形状）

Agent Skills 是开放格式（CodeBuddy / Claude Code / Codex / Cursor 同读一份 `SKILL.md`）。其官方规范与插件文档给出的「按需」机制是**声明式**的，而不是「预置一份备用副本」：

| 生态机制 | 原文要点 | 对我们的含义 |
|---|---|---|
| Bundled Resources | `scripts/` / `references/` / `assets/` 三类均可选，随 skill 一起落地 | 资源随包分发是**正常做法**，组件目录也一样 |
| `${CLAUDE_SKILL_DIR}` / `${CLAUDE_PLUGIN_ROOT}` | 引用随包脚本用变量，且在同一 skill 的 `allowed-tools` 里复用可免权限提示 | 组件内脚本必须用「相对安装根」定位，不写死绝对路径 |
| `${CLAUDE_PLUGIN_DATA}` | 「**跨更新存活的持久数据目录**，用于已安装依赖、生成文件、缓存」 | **可写状态（凭据/实例配置/运行时）绝不放组件目录**，必须放项目侧 |
| `skillOverrides`（四态）/ `/plugin` | `on` / `name-only` / `user-invocable-only` / `off`；插件级装卸走 `/plugin` | 「装了」与「开着」是两件事 ⇒ 我们要有**显式状态判定** |
| `shell: bash` 缺失 | 「**在任何命令执行前失败**」并明确报错；一条命令失败会中止整个 skill 调用 | 缺依赖/半装必须**硬失败**，不得静默降级 |
| `compatibility` 字段 | 「Claude Code 接受该字段但**不据此行动**」 | 别把「文档里写了前提」当成运行时保证 |

出处：`https://code.claude.com/docs/en/skills`、`https://www.codebuddy.ai/docs/zh/ide/Features/Skills`。

### 本宿主的差异（必须显式承认）

CodeBuddy 当前只有 skills / MCP / subagents，**没有 plugin marketplace，也没有 `skillOverrides`**。因此「按需安装」只能由**安装器开关 + manifest 声明**模拟。模拟时必须照抄生态的**形状**（声明式启用 + 状态可判 + 缺依赖硬失败），不得自创「休眠副本」形状。

## 三、四条硬约束

### L1 位置与主从（三处，职责唯一）

| 位置 | 语义 | 可写 |
|---|---|---|
| `<引擎仓库>/tools/<name>/` | **源**（唯一开发位置，纳入版本库） | 是 |
| `<项目根>/tools/<name>/` | **活实例**（凭据 / 实例配置 / 日志 / runtime 只允许落这里） | 是 |
| `<skill>/…`（任何位置） | **不存放组件副本** | 否 |

理由：组件一旦进了 skill 目录就成了第二份源（无人负责更新），且极易被误当成活实例；`${CLAUDE_PLUGIN_DATA}` 的存在说明生态也把「可写」与「随包」严格分开。

### L2 唯一入口 + 裸跑硬拒

- 安装/启用**只经** `<项目根>/tools/<name>/install-all.ps1`（或组件自带安装器），且必须显式给出项目根。
- 安装器的「复制」必须委托给**组件自己的**拷贝实现（排除清单只能有一份所有者）。在 skill 安装器里再写一份排除清单 ⇒ 必然漂移 ⇒ 泄漏凭据。
- 宿主级动作（自启快捷方式 / 计划任务 / 常驻进程 / 固定端口）**一律不由 skill 安装器代跑**：这些是单机单实例，第二个项目跑一遍会静默顶掉第一个。
- 组件安装器检测到「自身不在 `<项目根>/tools/<name>` 下且未显式给项目根」⇒ **exit 1**，不得猜路径。

### L3 状态三态（必须可判，且判据唯一）

| 状态 | 判据 | 含义 |
|---|---|---|
| `missing` 未分发 | 活实例目录不存在 | 组件未安装 |
| `staged` 已分发未启用 | 目录在，但 manifest 的启用开关不是启用值 | 文件就位、能力**未生效**（最容易误读的一态） |
| `enabled` 已启用 | 目录在 **且** 启用开关 = 启用值 | 真正生效 |

- 启用开关的**唯一事实源**是该组件在 `project/project.manifest.yaml` 里的声明（qqbot 即 `notifications.adapter: "qqbot"`）。不得另设「目录存在即启用」「某个环境变量即启用」等第二判据。
- 安装器的状态输出必须打印三态并给出下一步命令；`-DryRun` 也打印状态（预览兼查询）。

### L4 生命周期对称

| 动作 | 由谁做 | 判据 |
|---|---|---|
| 安装（分发） | skill 安装器（仅拷贝） | 状态从 `missing` → `staged` |
| 启用 | 用户在该项目执行组件安装器 | `staged` → `enabled`（改 manifest + 注册宿主级载体） |
| 升级 | 重跑 skill 安装器（引擎→活实例整替） | 实例文件（凭据/配置/日志/runtime）**不得**被覆盖 |
| 停用 | 把启用开关改回中性值 | `enabled` → `staged`，不动文件 |
| 卸载 | 先撤宿主登记（hook / 计划任务 / 自启），再删目录 | 回到 `missing` |

## 四、新增一个可选组件的检查清单

1. 源目录放**引擎仓库顶层** `tools/<name>/`（不要放 `engine/`——那个目录会被安装器「先删后拷」整替）。
2. 组件自带 `install-all.ps1`，且提供 `-CopyOnly`（只复制即退）与 `-DryRun`（只报计划）。
3. 排除清单（实例配置 / 凭据 / 日志 / runtime）**只写在组件内**一处；引擎 `.gitignore` 与同步脚本按需同步（当前三处：组件内 / 同步脚本 / 引擎 `.gitignore`）。
4. skill 安装器只加**开关 + 委托调用 + 状态输出 + 半装断言**，不写拷贝细节。
5. 判定启用值的正则与组件安装器**同款**（同一事实只认一个形状，避免两套判定漂移）。
6. 文档三处同步：`README.md`（中英）、`quickstart.md`（安装期询问话术）、组件自身 `README.md`（入口与卸载）。
7. 治理账本两处补记：`engine/consistency-checklist.md`、`engine/evolution-safety.md`。
8. 验收必须含**负向用例**：源缺组件 ⇒ 安装器 exit 1 且零落盘；组件安装器裸跑 ⇒ exit 1。

## 五、明确不做：skill 内预置「休眠副本」

曾评估「安装 skill 时把组件复制到 skill 目录，作为以后安装的来源」。**不采纳**，理由：

1. **陈旧**：副本没有更新责任人，组件升级后副本仍是旧版（对比：生态靠整装更新消灭陈旧态）。
2. **状态分裂**：副本 + 活实例 + 启用开关 = 三处状态，且没有一处能回答「到底启用没启用」。
3. **误跑静默**：在副本目录内直接跑组件安装器，会把凭据/实例配置装到错误位置，而通知适配层只在项目根找脚本 ⇒ 「装好了但全静默」，与 L2 的 fail-closed 方向相反。
4. **成本未换来覆盖**：唯一收益是「手上没有引擎仓库也能后装」，而该场景下引擎本身也无法升级，属既有限制。

**重新考虑的触发条件**（出现任一条时再评估，且必须带版本戳 + 只读 + 裸跑硬拒）：

- 需要把 skill **连同项目**交付给拿不到引擎仓库的人（外包 / 客户现场）；
- 需要给非开发者「双击安装」的体验；
- 引擎仓库不再作为常驻开发副本存在（改为纯发布制）。

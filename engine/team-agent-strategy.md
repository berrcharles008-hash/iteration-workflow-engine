# Team Agent 四维并行决策策略

> 从 SKILL.md 04 阶段 Step 2 提取。定义主 Agent 如何决定最优并行方案。
> **完全通用**，不包含项目特定内容。

---

## 一、核心原则

> 不要照搬固定的串行/并行模式。主 Agent 必须根据当前迭代的具体情况，按以下 4 个维度**动态决策**并行度。

---

## 二、四维决策算法

### 维度一：依赖类型

| 依赖类型 | 是否必须串行 | 判断标准 |
|---------|:---------:|---------|
| 导入依赖（A `import` B） | ❌ 不必 | 文件名和路径已在方案中确定，两个文件可同时写 |
| 接口依赖（A 调用 B 的方法，方案已定义签名） | ❌ 不必 | 方案已约定 API 形状，写 A 的 Agent 不需要 B 先存在 |
| 探索依赖（A 需要先读取 B 的当前内容才能写） | ✅ 必须串行 | 修改老文件追加/替换代码时 |
| 冲突依赖（A 和 B 修改同一文件） | ✅ 必须串行 | 同一文件不能被两个 Agent 同时修改 |

### 维度二：操作类型

| 操作类型 | 风险 | 并行建议 |
|---------|:--:|---------|
| 新建文件（从无到有） | 低 | ✅ 可大胆并行 |
| 追加到已有文件 | 中 | ⚠️ 每个 Agent 需先 `read_file`，但可并行读取 |
| 替换已有代码 | 高 | ❌ 建议串行，逐个确认 |
| 只读探索（code-explorer） | 无 | ✅ 可与其他任务完全并行 |

### 维度三：方案完整度

| 方案中代码的完整程度 | 并行策略 |
|-------------------|---------|
| 完整代码已写入方案 | **近乎全并行**——所有文件内容已知，Agent 只是"抄写" |
| 只有接口签名 | 按依赖关系分阶段串行，先底层后上层 |
| 只有描述没有代码 | 先派探索 Agent 读代码库，再串行实现 |

### 维度四：改动文件数量

| 文件数 | 策略 |
|-------|------|
| 1-2 个 | 不必建 Team，主 Agent 直接 `write_to_file` |
| 3-5 个 | 建 Team，2-3 Agent 并行 |
| 6+ 个 | 建 Team，按依赖图**分批**并行，**每批 ≤3**（受维度五硬约束，不再"最大化并行"） |

### 维度五：宿主承载上限（★ 硬约束，优先级高于维度一~四）

> **实测背景**：CodeBuddy 扩展宿主（Extension Host）在过载时会异常终止
> （平台注入提示原文：`the CodeBuddy extension host terminated unexpectedly ... its pending
> tool calls and any team members were stopped`）。终止瞬间**在途任务、待执行工具调用和所有
> Team 成员一并停止**，成员未回传的产出即丢失。
> 因此并行度不能只按依赖最大化，必须同时满足下列上限：

| 约束 | 阈值 | 依据（通用理由；宿主专属实测见脚注 †） |
|------|------|------|
| 同批并行成员数 | **≤ 3** | 协调开销与故障域隔离（并行度越高，单点故障波及面越大） |
| 单成员**与 lead 会话**上下文 | **≤ 15 万 token** | 上下文成本：单轮耗时随会话规模近线性增长（2026-09-29 起本行覆盖 lead 会话） |
| 单成员 max_turns | 新建 ≤3、追加 ≤8、探索 ≤2 | 见 §七 |
| 单成员消息规模（运行中观测） | **msgs ≤ 50** | 单轮耗时随上下文线性增长；>50 即拆分粒度不足征兆（2026-09-29 实证） |

> † **CodeBuddy 侧实测证据（宿主专属，非通用理由）**：09-24 六路并发 15 分钟内崩 3 次 / 09-23 四路 5 分钟内崩 1 次 /
> 09-24 14:58 崩溃发生在单会话 15.7 万~28.6 万 token 时 / 09-29 be-saveuser 滚到 msgs=130、35+ 分钟无产出。
> ★ lead 会话实测：09-29 达 209,163 → 343,988 token（阈值 2.3 倍）⇒ 本表第 2 行的 lead 覆盖即由此而来。

**超阈值处理**（不得硬闯）：
- 并行成员 > 3 → 拆成多个 Batch 串行派发，**不得**同批派发第 4 个
- 单成员（或 lead）上下文预计 > 15 万 token → 拆任务；或让成员 `read_file` 精准片段，禁止整仓扫描；
  lead 侧同受此限（收集/写入阶段走定点读 + 引用式汇总）

## 三、决策执行流程

> **Step 0（★ 2026-09-24 新增；`[CodeBuddy-only]`）**：派发前挂载崩溃监控采样器
> （命令见 `phase-04.md` Step 2.0：`tools\eh-monitor.ps1`）。
> ★ **仅 CodeBuddy 宿主执行**；非本宿主（Claude Code 等）**静默跳过**本步，改用 §八 通用恢复判据。
> 理由：宿主崩溃**根因未定性**，平台抓取的 cpu profile 存于 `%TEMP%\codebuddy-starvat*`
> 且会被清理，不挂采样器则事后永远拿不到成因证据。

```
Step 1: 扫描技术方案，列出所有任务
Step 2: 标注每个任务：操作类型（新建/追加/替换）、文件是否已知内容
Step 3: 按 4 个维度计算最优派发方案
Step 4: 输出「任务依赖图」+「并行分组」→ 强制用户确认
Step 5: team_create → 按分组批量 task 派发（同批 ≤3，见维度五）
        ★ 每个成员 prompt 必须含【产出落盘】段（见 §七）：成员每完成一个文件即增量落盘
Step 6: 主 Agent 收集所有 Agent 输出 → 生成统一变更预览
        ★ "完成"= 双层判据（2026-09-29 修订）：
          ① 写入已停止：team-out 的 TEAM-OUT-COMPLETE 标记（+ 目标文件 LastWriteTime，
             直写模式下降级为「在产出 vs 空转」判别）；
          ② 产出正确：svn diff 真实 diff 核对（白名单直写批次以②为准）。
        界面成员状态仅作参考——已知平台缺陷见 §九
Step 7: 用户一次确认 → 主 Agent 批量写入所有文件
Step 7.5: ★ 等待用户确认的方式（**细则唯一来源 = `engine/waiting-protocol.md`**（三选一 A/B/D + 时限/退化/铁律）；
        本节仅保留**宿主相关增量**，不再复述细则）：
        · waiter 成员命中答案后 **send_message 唤醒主 Agent** —— 2026-09-29 已端到端实测；单片 900s 长跑亦已实测；
        · ★ **该唤醒通道仅在 lead「首次派发后结束回合」时可用（2026-10-03 三例实证）**：lead 回合结束即
          `stopping inbox polling`，被唤醒后的回合再派新成员也不重建等待态 ⇒ 成员→成员唤醒不成立，
          派发后结束回合必须输出"完成后请发消息唤醒"提示（细则 = `phase-04.md` Step 2 人工唤醒协议）；
        · ★ **Claude Code**：`-p` 不生成队友 ⇒ 该宿主下退化为**主 Agent 直跑**（见 §六-b）；
        · ★ **等待中不做其它写操作**（避免与接管撞车；与 Step 1.6 的"禁绑回复即起新会话"互补）。
Step 8: ★ 若出现「extension host terminated unexpectedly」提示 → 立即转 §八 宿主中断恢复；
        成员长时间无响应 → **先走 §九 判别清单定性**（≠必然崩溃）再干预；
        **禁止**假设已完成并直接重派全部任务
```

> ⚠️ **Step 5 的结构性风险**：成员"只输出不写文件"意味着产出**仅存在于回传消息中**，
> 一旦宿主终止即随消息丢失。因此 §七 的落盘要求是**强制补偿措施**——落盘的是产出记录
> （`{IDE}/temp/team-out/`），业务代码仍由主 Agent 在 Step 7 统一写入，两者不冲突。

## 四、决策输出格式（主 Agent 必须输出此格式）

```
=== 并行策略分析 ===
文件数: {N}
方案完整度: {完整代码已知/只有签名/只有描述}
冲突检测: {无同文件修改/存在冲突 → 串行}

决策: 分 {N} 批并行
  Batch 1（并行，{N} 个 Agent）:
    {agent-name-1} → {操作类型} {文件}
    {agent-name-2} → {操作类型} {文件}
  Batch 2（并行，等 Batch1 全部完成）:
    {agent-name-3} → {操作类型} {文件}

效率对比: {N} 轮 vs 固定串行 {M} 轮，节省 {%}
```

## 五、示例：完整代码在方案中的最优并行（6 个文件）

```
分析结果：
  - 所有文件内容已在方案中 → 维度三=全并行
  - 新增文件5个、追加1个 → 维度二=低风险
  - 无冲突依赖（未修改同一文件）→ 维度一=无串行约束
  - 文件数=6 → 维度四=建 Team

决策：分2批并行！
  ┌─ Batch 1（并行派发，无依赖）─────────────────┐
  │ agent-net     → 新建 Net 层文件               │
  │ agent-bll     → 新建 BLL 层文件               │
  │ agent-explore → 读取目标 domain 文件当前内容   │
  └──────────────────────────────────────────────┘
            ↓ 全部完成后
  ┌─ Batch 2（并行派发）──────────────────────────┐
  │ agent-domain  → 追加 Domain 层方法（需探索结果）│
  │ agent-page    → 新建页面 .vue + .ts             │
  │ agent-route   → 修改路由配置文件                │
  └──────────────────────────────────────────────┘

对比固定模式（串行 Net→BLL→Domain→Page→Route，4轮）：
动态决策后只需2轮，效率翻倍。
```

## 七、派发参数规范

```
task 参数：
  subagent_name: "code-explorer"   （只读探索时使用）
  mode: "default"                   （标准模式）
  name: "{角色名}"
  team_name: "{team_name}"
  max_turns: {新建=3, 追加=5~8, 探索=2}
```

> 注意：`mode` **默认**不使用 `bypassPermissions` 或 `acceptEdits`。Team Agent **默认**仅输出**业务代码**不写入业务文件，业务代码写入由主 Agent 在批量确认后统一执行（见 §三 Step 6-7）。
>
> ★ **白名单试点例外（2026-09-29 新增，默认关闭）**：仅当派发 prompt **显式列出白名单文件**且用户批准试点时，
> 该批次允许成员以 `mode=acceptEdits` 直写**白名单内**文件（同文件唯一 owner + 原子写）；白名单外一律沿用默认路径。
> 白名单须**双写**（本节 + `phase-04.md` Step 2 派发模板），**越界即回收白名单**并退回默认。
> ★ **门禁层硬化（2026-09-30 新增 · E-3）**：白名单同时下传为**门禁可读元数据** = `runtime/{ITERATION_ID}.state.yaml` 的
> `dispatch_whitelist:` 段（条目 `- "路径"`，**双副本同步**：`.codebuddy` 为源 / `.claude` 为判定源）。
> 门禁在 **04 阶段**按**四档**处置：无段=关闭 · ≥1 条=启用（越界 ⇒ `block` + `WHITELIST_BLOCK` 留痕）· 空数组=`WHITELIST_DISABLED` 留痕 ·
> 解析异常=`WHITELIST_PARSE_FAIL` 留痕并放行；覆盖**仅写类工具**（`Write`/`Edit`；Bash 与 Delete 不在其列）。
> **清除时点 = 04 收口**（删段 + 双副本同步 ⇒ 05-07 恢复旧路径）；生效期主 agent 写非白名单同样受限（hook 无 role 字段）。
>
> **★ 例外：产出记录必须落盘**（宿主崩溃时回传消息会丢失，因此产出不能只存在于消息中）。

### 【产出落盘】段（每个成员 prompt 必含，原样复制）

```
【产出落盘（★ 强制，防宿主崩溃丢失）】
每完成 **一个** 文件，立即把该文件的完整产出追加写入：
    {IDE}/temp/team-out/<你的成员名>.md
原子写（防崩溃产生半截文件）：
    1) 先写同目录 <成员名>.md.tmp
    2) 再 rename 覆盖 <成员名>.md
每段格式：
~~~
## <文件相对路径>  操作：新建/修改  +行数
<代码块：完整内容或 diff>
- 自检：<本节自检结果>
~~~
全部完成后追加完成标记：
    <!-- TEAM-OUT-COMPLETE files=N -->
禁止：
- ❌ 产出只放在回传消息里、不落盘
- ❌ 全部做完后才一次性写（中途崩溃则全丢）
- ❌ 越出白名单写入（默认：业务代码仍由主 Agent 统一写入；白名单试点批次的白名单内文件除外）
```

### 【任务范围与报告上限】段（每个成员 prompt 必含，原样复制；★ 2026-09-29 实证新增）

> **依据**：be-saveuser 任务最大 → 30 分钟滚到 130 条消息 + 写出 42KB 超长报告，尾部 27 分钟
> 全耗在扩展阅读与报告上（兄弟成员限内完成仅 8/16KB）。

```
【任务范围（★ 防轮次爆炸 + 上下文膨胀）】
- 只读以下文件，严禁读取清单外文件、严禁全库扫描/自由扩展阅读：
    <逐个列出文件绝对路径>
- 大文件（>500 行）只准定点读：read_file 带 offset/limit（单次 ≤80 行），禁止整读、禁止同文件反复重读
- ❌ 禁止执行任何 shell/编译/语法自测命令（会触发用户确认弹窗，而确认请求不会提示主会话，
  成员将静默卡死）；语法/编译校验由主 Agent 收口时统一执行
- 报告长度上限 ≤ 16KB：只写各文件产出 + 一行自检结论，不写展开解释
- 每完成一个文件先落盘（见【产出落盘】），再做下一个
- 业务代码写完即达成本任务，不主动追加"顺便"的优化或补读
```

## 八、宿主中断恢复（★ Extension Host 终止后必走）

> 本节原名「崩溃恢复协议」（2026-09-29 更名：宿主无关化，机制与判据不变）。
> ★ **Claude Code 差异**：in-process 队友**不随 `/resume` 恢复**（CodeBuddy 成员可 respawn）⇒
> 该宿主下[「先核对磁盘、不假设」](#)判定与 §七 增量落盘是**唯一**恢复依据，重派步骤按 §六-b 映射表退化。

> 依据平台注入提示原文：
> "the CodeBuddy extension host terminated unexpectedly, so the in-flight task, its pending
> tool calls and any team members were stopped. Before continuing, **verify what was actually
> produced (files on disk / member messages)**, then re-run or reassign whatever is still
> missing instead of assuming the previous work completed."

**适用触发**（命中任一即进入本协议）：
- 会话中出现 `extension host terminated unexpectedly` 提示
- 成员状态停在 `running` 但长时间无新产出、无回传
- 日志出现 `EH lifecycle — initialize phase begin, 31 components`（= 宿主冷启动，见排查入口）

> ⚠️ **成员久无响应 ≠ 必然崩溃**（2026-09-29 实证教训）：be-saveuser 35+ 分钟无消息，
> 同环境兄弟成员正常完成、eh-monitor 全程无 HOST_STARVATION ⇒ 根因是成员自身轮次爆炸+
> 上下文膨胀，不是宿主。先走 §九 判别清单定性，EH 无事件 + msgs 膨胀 = 慢成员，按 §九 干预。

**恢复步骤**（顺序不可颠倒）：

1. **先核对磁盘，不假设**：读 `{IDE}/temp/team-out/*.md`，按 `TEAM-OUT-COMPLETE` 标记
   把成员产出分为「已完成 / 半截 / 未开始」三类
2. **再核对业务文件**：确认哪些目标文件已在磁盘上产生；半截文件须人工确认能否保留
3. **只重派未完成部分**：已完成的不重派，半截的从断点续，未开始的按原 prompt 重派
4. **重派时注入上下文**：把已落盘的 `<成员名>.md` 路径写进新成员 prompt，令其
   **读文件接续**，而非从零重新读代码
5. **留痕**：本次「崩溃 → 影响面 → 恢复动作」记入 `project/lessons-learned.md`

**禁止行为**：
- ❌ 假设上次已完成，直接推进下一步
- ❌ 不区分状态、重派全部成员（重复消耗 + 引入重复改动）
- ❌ 把半截文件当完成

## 九、慢成员预防与干预协议（★ 2026-09-29 实证新增）

> **实证背景**：team 2801-dim-converge-dev 中 be-saveuser 35+ 分钟无消息，同环境兄弟成员
> 4.5/12 分钟完成 ⇒ 排除环境饥饿（eh-monitor 全程无 HOST_STARVATION）。
> **根因 = 任务最大 → 30 分钟滚到 130 条消息**（大量重读/小步规划），单轮耗时随上下文
> 线性变慢；业务代码 09:16 已写完，后 27 分钟耗在扩展阅读 + 写 42KB 超长报告
> （兄弟成员仅 8/16KB）。与 §八 的宿主崩溃是**两类独立现象**。

**预防三措施（派发前落实，治本）**：
1. **重任务必须拆小**：单成员控制在 2~3 个文件 / 一层职责以内（压制 msgs 上限）
2. **prompt 限定只读范围**：成员 prompt 必含 §七【任务范围与报告上限】段，禁读清单外文件
3. **限制报告长度**：≤ 16KB（对照：限内成员 8/16KB vs 失控 42KB）

**判别清单（成员久无消息时，先定性再动手）**：
1. `.codebuddy/teams/<convId>/<team>/config.json`（★ **[CodeBuddy-only]**：本项为 CodeBuddy **项目级**路径；
   Claude Code 侧队友元数据在**用户级**目录、且本项目内无对应物 ⇒ 该宿主跳过本步）看成员 status / sessionId
2. IDE 日志（`%LOCALAPPDATA%\CodeBuddyExtension\Logs\CodeBuddyIDE\<日期>\<工作区>__*.log`）
   按成员 sessionId 过滤：最近活动时间戳 + `Slow index update ... msgs=N`，
   **msgs 数 = 会话规模指数**（>50 = 拆分粒度不足征兆，对照维度五阈值）
3. 业务目录 LastWriteTime：最后写盘时间 vs 当前 ⇒ 区分"在产出" vs "空转"
4. `{IDE}/temp/team-out/<成员>.md` 持续增长 ⇒ **已在收尾落盘，别掐断**；
   停止增长且会话仍活跃 ⇒ 空转，可干预

**干预手段**：
- 轻度：lead 会话向该成员发收口指令（停止扩展阅读、立即落盘、回 DONE）
- 重度：shutdown 后拆小重派，重派 prompt 注入已落盘 `<成员名>.md` 路径令其接续（同 §八 第 4 步）
- ⚠️ `.stop`/团队标记类文件是**全局共享**的，多实例并存时不能用它停单个成员

**收尾对账（措施有效性验证）**：编码收尾时按成员对账 ① msgs 数（>50 = 拆分不足）
② team-out 报告大小（>16KB = 约束失效），超标项与整改动作回写 `project/lessons-learned.md`。

- **零改动防线（已生效；2026-09-29 修订为双层）**：成员"完成"判定只认磁盘证据 ——

  ② **产出正确**：`svn diff` 真实 diff 核对（**直写白名单批次以②为主体**；本清单第 3 步
  LastWriteTime 降级为「在产出 vs 空转」判别）。界面状态仅作参考。

# 迭代文档版式规范（Doc Style Guide）

> **适用**：01~07 阶段产出的全部迭代文档（`{{ITERATIONS_DIR}}/`）。
> **一句话**：表格只放短字段，长内容用列表；结论在前，过程在后。
> **自检**：`python scripts/doc_lint.py <文档或目录>`（相对 skill 目录；ERROR 必修，WARN 人工判断）
> **SSOT**：本文件是文档版式的唯一权威来源；模板与阶段文件只引用、不重复定义。

---

## 一、四条核心原则

| # | 原则 | 理由 |
|:--:|:--|:--|
| P1 | **表格放短字段，不放段落** | 单元格超 60 字后，渲染宽度被列数挤压，视觉上成为"面条"，不可读 |
| P2 | **结论在前，过程在后** | 读者 90% 的时间只关心"现在是什么结论"；取证明细、评审流水属少数场景 |
| P3 | **正文只写当前生效态** | 过程痕迹（"XX 阶段修正""已修订"）留在正文，每轮迭代叠加一层，越读越乱 |
| P4 | **一份文档一种编号轨** | 中文序号 + 阿拉伯点号 + 业务码混排，交叉引用无法定位 |

---

## 二、八条硬规则（doc_lint 自动检查）

| # | 规则 | ERROR 阈值 | WARN 阈值 |
|:--:|:--|:--|:--|
| D1 | 表格单元格长度 | > 200 字符 | > 60 字符 |
| D2 | 正文单行长度（代码块/表格行/链接行除外） | > 300 字符 | > 120 字符 |
| D3 | 粗体密度（`**` 对数 ÷ 总行数） | — | > 1 : 10 |
| D4 | emoji 白名单外的符号 | — | 出现即报 |
| D5 | 单个代码块行数 | > 80 行 | > 40 行 |
| D6 | 表格列数 | — | > 6 列 |
| D7 | 文档头元信息块（前 12 行内含"迭代 ID"） | 缺失 | — |
| D8 | 结论摘要小节（前 60 行内含 `## 结论摘要`） | 缺失 | — |

**emoji 白名单**（D4）：✅ 完成 ｜ ⬜ 未开始 ｜ ⏳ 进行中 ｜ ⚠ 风险 ｜ ❌ 失败 ｜ 🔴 复杂/阻塞 ｜ 🟡 中等/严重 ｜ 🟢 简单 ｜ 🔵 轻微。

> **豁免**：`*.csv` / `*.json` 等数据文件不适用；确需保留长单元格的证据附件，可在文首加
> `<!-- doc-lint: allow D1 -->` 单规则豁免（其它规则仍检查）。

---

## 三、六条文风纪律（人工遵守）

| # | 规则 | 常见反例 |
|:--:|:--|:--|
| S1 | 粗体只标"结论 / 数字 / 风险"，每节 ≤ 5 处 | 每句 3 处加粗，等于没有重点 |
| S2 | 引用块 `>` 只用于"依据来源"，集中放小节末尾 | `> 依据：…` 插在正文中间，割裂阅读 |
| S3 | 业务码首现给全称（`AC-3` → `AC-3（验收判据 3）`） | 满篇 `M8 / WP / UC / BLK` 无解释 |
| S4 | 过程痕迹不进正文（`（02 评审新增 · ★03 修正）`、`✅ 已修订` → 附录） | 结论与演进过程混排，读者分不清哪个是当前结论 |
| S5 | 一段只讲一件事，超过 8 行拆小节 | 大段文字无分段 |
| S6 | 状态符号语义唯一（见白名单），✅ 不兼表"已修订/已验证" | 一个符号三种含义 |

## 四、标准骨架（所有阶段文档统一）

````markdown
# <0X>-<文档名> · <迭代名称>

| 项 | 值 |
|:--|:--|
| 迭代 ID | `YYYY-MM-DD-NNN-<名称>` |
| 阶段 | 0X-<阶段名> |
| 状态 | ⏳ 进行中 / ✅ 已确认 |
| 复杂度 | 🟢 简单 / 🟡 中等 / 🔴 复杂 |
| 上游文档 | [01-需求记录](../01-需求分析与设计/01-需求记录.md) |
| 更新时间 | YYYY-MM-DD |

## 结论摘要

- **结论**：一句话说清本文档最终结论
- **关键决策**：N 项（无则写"无"）
- **下一步**：谁做什么

## 1. <正文主题>

### 1.1 …

> 正文只写当前生效结论；表格列 ≤ 6 列、单元格 ≤ 60 字

## 待办与风险

| # | 事项 | 落点 | 状态 |
|:--:|:--|:--|:--:|

## 附录 A · 过程记录

> 评审处置明细 / 变更历史 / 取证明细 —— 只增不改，读者可跳过。

## 附录 B · 变更记录

| 日期 | 内容 |
|:--|:--|
````

**编号规则**：章节统一阿拉伯数字 `1.` / `1.1`（不用"一、二、三"混排），跨文档引用写成
`[03-技术方案 §4.2](../03-技术方案/03-技术方案.md)` 形式。

## 五、长内容的两种写法（替代表格）

### 5.1 任务 / 改动条目 —— 标题 + 缩进列表

**反例**（表格单元格塞 700 字，渲染后不可读）：

```markdown
| 编号 | 类型 | 文件路径 | 代码片段 | 验证步骤 | 状态 |
| T1-6 | MODIFIED | `src/bll/OrderMgr.cs` | ①`BuildFilter` 增 Status 条件（null→默认启用；-1→不加条件；0/1→等值）②`ToDto` 增新字段 ③`Save` 更新分支改显式列 UPDATE（`affected == 0` → `[ERR_NOT_FOUND]`，不再全列绑定）④`GetById` ⑤`Sync`/`Upsert`/`LoadIndex`/`MapCategory`/`BuildSourceSql`/`ExecuteUpdate`/`WriteLog`/`TryEnter`/`Exit`/`Cut`/`Eq`（★含并发残余窗口声明注释：同步-同步进程内互斥 / 同步 vs 编辑窗口一期接受）⑥`using System.Diagnostics;`…（同类单元格实测曾达 700+ 字符） | 编译通过 + 实跑 | ✅ |
```

**正例**（表格只留短字段，细节下沉为列表）：

````markdown
| 编号 | 类型 | 文件路径 | 状态 |
|:--:|:--:|:--|:--:|
| T1-6 | MODIFIED | `src/bll/OrderMgr.cs` | ✅ |

#### T1-6 · `src/bll/OrderMgr.cs` — MODIFIED ✅
验证：编译通过 + 实跑

- 新增 `GetById` / `Sync` 及配套私有方法 `Upsert` `LoadIndex` `MapCategory` `Cut` `Eq`
- `BuildFilter` 增 Status 条件：`null → 默认启用`、`-1 → 不加条件`、`0/1 → 等值`
- `Save` 更新分支改显式列 UPDATE（`affected == 0 → [ERR_NOT_FOUND]`）
- ⚠ 并发：同步-同步进程内互斥；同步 vs 编辑窗口一期接受；跨范围并发不在本期
````

## 六、自检

```bash
# 整迭代
python scripts/doc_lint.py docs/iterations/<迭代ID>
# 单文件
python scripts/doc_lint.py docs/iterations/<迭代ID>/04-开发实现/04-开发任务清单.md
```

- **ERROR** ⇒ 生成后必须修（计入阶段交付标准）；
- **WARN** ⇒ 人工判断，多数情况应修。

> 生成文档的 Agent 在写入前自检一次；主 Agent 在阶段收口时对全阶段文档再跑一次。
